# SixSevenDB Codebase Audit

**Date:** 2026-06-09/10
**Scope:** Four dimensions: (1) duplicate/unused code, (2) tests that do not actually test anything, (3) hardcoded/fake/brute-force implementations, (4) design inconsistencies and poor UX.
**Method:** 38 finder agents read all 344 test files and 11 of 15 source-module partitions in full. Each finding was scheduled for independent adversarial verification; the verification phase was interrupted (monthly API spend limit), so verification status is stated per finding below. All 7 critical findings and all 43 high findings were re-verified by hand against the source (phase-1 triage, 2026-06-10); three claims were additionally reproduced by running the QA binary. Medium/low findings remain unverified leads.

## Executive summary

The storage, B+ tree, MVCC, WAL, and HNSW *structures* are substantively implemented; this is not a stub codebase. But the audit found a consistent pattern: **correct cores wrapped in unwired or silently-wrong edges.** Specifically:

0a. **Secondary indexes go stale on every write (phase-3, verified):** B+tree and hash indexes are populated only at CREATE INDEX/REINDEX; INSERT/UPDATE/DELETE never touch them, so indexed queries silently miss new rows and return deleted ones. See section 2d.
0b. **There are no transactions (phase-2, verified):** `BEGIN`/`COMMIT`/`ROLLBACK` return errors over the wire, every statement auto-commits, the entire `src/txn/` module (MVCC, locks, deadlock detection, vacuum) is production dead code, and updates overwrite tuples in place with no versioning and no write-write conflict detection. See section 2c.
1. **Silent wrong results (verified critical):** `ROLLBACK TO SAVEPOINT` commits work it claims to roll back; FLOAT/DECIMAL inserted into integer columns store `0`; `NEAREST ... USING DOT` returns the *least* similar rows; the HNSW index navigates with L2 regardless of declared metric; undirected multi-hop `MATCH` binds wrong nodes or drops half its expansions.
2. **The QA suite is structurally broken at HEAD (verified):** at least 10 `test_qa_gdb_*` suites fail in `SetUp` (`database with id 1 not found`, regression from GDB-655) and one unchecked `Result` dereference aborts the whole QA binary, masking everything after it. The regression safety net largely does not run.
3. **Features that exist but are not wired in (verified):** crash recovery never invoked by the server binary, the cost-based optimizer/statistics are decorative, `--standby` replication is unreachable, external sort is never planned, per-session `SET` variables are accepted and ignored.
4. **The "22 types" claim is oversold:** DECIMAL precision/scale are parsed then discarded, DECIMAL arithmetic falls back to float, 11 of 23 value types hash to a constant (degrading hash indexes to linear scans).

## 1. Critical findings (all VERIFIED by hand)

### C1 NEAREST ... DOT returns the k LEAST similar rows (dot product sorted ascending)
- **Location:** `src/executor/planner.cpp:2543`  
- **Category:** design-inconsistency | **Severity:** critical | **Found by:** `impl:vector`

to_distance_metric maps `NearestMetric::DOT -> DistanceMetric::DOT_PRODUCT` (planner.cpp:2542-2543). distance.h:19-21 documents DOT_PRODUCT as 'Raw dot product ... Higher values indicate more similar vectors', and compute_distance returns the raw (un-negated) dot (distance.cpp:400-401). But NearestScanOperator::execute_brute_force sorts candidates by 'distance ASC' (nearest_scan.cpp:134-137) and takes top-k; execute_prefiltered_search does the same (line 195 + ascending sort). There is no descending/negation special-case for DOT anywhere in nearest_scan.cpp. DistanceMetric::INNER_PRODUCT (the negated variant documented 'Lower values indicate more similar vectors (suitable for HNSW)', distance.h:23-25) has zero production callers — it is referenced only in tests (test_distance.cpp, test_qa_gdb_30.cpp).

**Why it matters:** The DOT metric is reachable from user SQL (parser.cpp:2364 parses it), and any NEAREST query using it silently returns the k most DISsimilar rows — inverted results, no error. The INNER_PRODUCT enum value that exists precisely to make dot product sortable-ascending is dead code in production.

**Suggested fix:** Map NearestMetric::DOT to DistanceMetric::INNER_PRODUCT in to_distance_metric (and negate back when emitting _distance if raw dot is the desired display value), or sort descending when metric == DOT_PRODUCT. Add a regression test asserting the highest-dot row comes first.

> **Verification:** VERIFIED by hand. `to_distance_metric()` (`src/executor/planner.cpp:2538`) maps SQL `DOT` to `DistanceMetric::DOT_PRODUCT`. `compute_distance` returns the RAW dot product for `DOT_PRODUCT` (`src/vector/distance.cpp:400`, bigger = more similar) and only negates for `INNER_PRODUCT` (`:403`). `nearest_scan.cpp` sorts candidates by distance ASC and emits top-k, so `NEAREST ... USING DOT` returns the k LEAST similar rows. Corroborated independently by the test sweep: the GDB-131 QA test asserts the inverted ordering as expected behavior.


### C2 HNSW index hardcodes L2 distance, ignoring the query's requested metric (COSINE/DOT)
- **Location:** `src/vector/hnsw_index.cpp:952`  
- **Category:** design-inconsistency | **Severity:** critical | **Found by:** `impl:vector`

Every distance computation inside HnswIndex is hardcoded to L2: greedy_search_layer line 876 `compute_distance(DistanceMetric::L2, query, entry_vec.value())` and line 911, search_layer lines 952 and 1002 same. HnswIndexConfig (hnsw_index.h:20-25) has no metric field at all. Meanwhile the executor maps SQL NEAREST metrics via to_distance_metric (planner.cpp:2538, COSINE is the default per nearest_scan.h:35 `DistanceMetric metric = DistanceMetric::COSINE`), and NearestScanOperator::do_open (nearest_scan.cpp:49-53) prefers the HNSW path whenever the index has nodes. execute_hnsw_search emits the raw HNSW distance as the _distance column (nearest_scan.cpp:295 `matched.push_back({sr.distance, ...})`) and ranks by it (line 340), so config_.metric is never applied on the HNSW path. The brute-force path (nearest_scan.cpp:128) DOES honor config_.metric.

**Why it matters:** A NEAREST query using the default COSINE metric returns L2-squared rankings and L2-squared _distance values whenever an HNSW index exists (which is auto-created for every EMBEDDING column by EmbeddingColumnManager::register_table_embeddings). For non-unit-norm embeddings (Ollama, ONNX mean-pooled outputs are not normalized) the ranking itself is wrong, and in all cases the reported _distance differs from the same query on a table without an index — silent, metric-dependent wrong results on the mainline vector search path.

**Suggested fix:** Add a DistanceMetric field to HnswIndexConfig/HnswMeta, thread it through greedy_search_layer/search_layer (using INNER_PRODUCT for dot so lower=closer), persist it in the meta page, and have the planner verify the query metric matches the index metric (re-rank or fall back to brute force on mismatch). At minimum, recompute distances with config_.metric in execute_hnsw_search before sorting/emitting.

> **Verification:** VERIFIED by hand. All four `compute_distance` calls in the HNSW graph search (`hnsw_index.cpp:876`, `:911`, `:952`, `:1002`) pass a hardcoded `DistanceMetric::L2`, regardless of the metric the index or query was declared with. COSINE/DOT queries served through the HNSW index navigate the graph using L2 geometry.


### C3 fit_to_storage silently stores 0 when fitting FLOAT/DECIMAL values into integer columns
- **Location:** `src/common/coercion.cpp:435`  
- **Category:** fake-implementation | **Severity:** critical | **Found by:** `impl:common-cli`

fit_to_storage() narrowing branch: `if (is_numeric(val.type_id()) && is_integer(target)) { int64_t v = to_int64(val); return ok(int64_to_value(v, target)); }`. The helper to_int64() (lines 48-69) only handles the 8 integer TypeIds; its `default: return 0;` swallows FLOAT32, FLOAT64, and DECIMAL. Verified empirically by compiling a probe against build/debug/src/common/libsixseven_common.a: `fit_to_storage(Value(3.7), TypeId::INT32)` returns ok with value 0. Reachable from SQL: Binder::bind_insert (src/planner/binder.cpp:1962) accepts the column if can_coerce works in EITHER direction (can_coerce(INT32, FLOAT64) is true), and InsertIterator (src/executor/insert.cpp:111,154) then calls fit_to_storage on the evaluated value.

**Why it matters:** INSERT INTO t(int_col) VALUES (3.7) passes binding, returns success, and silently stores 0 instead of 3 (or an error). This is silent data corruption on a mainline DML path, and the same hole applies to UPDATE (src/executor/update.cpp:61).

**Suggested fix:** In fit_to_storage, handle floating/decimal sources explicitly (truncate via the validated explicit_cast float-to-int path) instead of falling into to_int64's default-0 case; or make to_int64 return Result and propagate a TYPE_ERROR.

> **Verification:** VERIFIED by hand. `fit_to_storage` (`coercion.cpp:435`) routes any numeric -> integer through `to_int64`, which has no FLOAT32/FLOAT64/DECIMAL cases and returns 0 from its `default:` arm (`coercion.cpp:67`). Inserting `3.7` into an INT column silently stores `0`.


### C4 fit_to_storage performs integer narrowing with no range check — silent wraparound
- **Location:** `src/common/coercion.cpp:434`  
- **Category:** fake-implementation | **Severity:** critical | **Found by:** `impl:common-cli`

Unlike explicit_cast(), which calls fits_in_integer() and returns make_error(TYPE_ERROR, "integer out of range") (lines 402-407), fit_to_storage's narrowing branch calls int64_to_value() directly with no range validation. Verified empirically: fit_to_storage(Value(int64_t{300}), TypeId::INT8) returns ok with value 44; fit_to_storage(Value(int32_t{-1}), TypeId::UINT32) returns ok with value 4294967295. Both are reachable from INSERT/UPDATE: the binder's bidirectional can_coerce check (binder.cpp:1962-1963) lets INT64 expressions through to narrower columns, then insert.cpp:111/154 and update.cpp:61 call fit_to_storage.

**Why it matters:** Inserting 300 into an INT8 column silently stores 44; inserting -1 into a UINT32 column silently stores 4294967295. Silent data corruption with a success result, while the sibling function explicit_cast correctly errors for the same conversions — users get strictly worse safety from implicit DML than from an explicit CAST.

**Suggested fix:** Call fits_in_integer() in the narrowing branch and return TYPE_ERROR ("integer out of range") on overflow, mirroring explicit_cast.

> **Verification:** VERIFIED by hand. The same `fit_to_storage` narrowing path calls `int64_to_value(v, target)` with no `fits_in_integer` range check, unlike the checked `coerce()` path directly above it (`coercion.cpp:402-408`). Out-of-range integers wrap silently. `to_int64` also casts UINT64 > INT64_MAX to negative (`coercion.cpp:65`).


### C5 Multi-hop MATCH with undirected (BOTH) edges binds the wrong target node
- **Location:** `src/executor/pattern_match.cpp:377`  
- **Category:** fake-implementation | **Severity:** critical | **Found by:** `impl:exec-graph-ops`

In PatternMatchOperator::execute_multi_hop, edge_rows under TraverseDirection::BOTH are collected from BOTH graph_engine_.get_edges_from() and get_edges_to(), then the neighbor is resolved as: `Value tgt_pk = (edge_def.direction == TraverseDirection::IN) ? edge_row.source_pk : edge_row.target_pk;`. For BOTH, edges fetched via get_edges_to (incoming edges Y->current) have target_pk == the current node, so tgt_pk is set to the current node itself instead of Y. The single-hop path (execute_single_hop, lines 158-178) does this correctly by resolving the neighbor per index (`Value nbr = e.target_pk` for fwd, `e.source_pk` for rev), proving the multi-hop copy diverged. Parser confirms undirected `-[r]-` produces TraverseDirection::BOTH (src/parser/parser.cpp ~2478) and Planner::plan_match passes it through unchecked.

**Why it matters:** MATCH (a)-[r1:e]-(b)-[r2:e]->(c) (any multi-edge pattern containing an undirected segment) silently emits spurious rows where b is bound to a itself, and never emits the real reverse neighbors. Wrong query results on a first-class syntax with no error. tests/unit/test_pattern_match.cpp only exercises BOTH for the single-hop path (line 350), so this is uncovered.

**Suggested fix:** Carry the resolved neighbor alongside each EdgeRow at fetch time (as execute_single_hop does with edges_with_neighbor pairs): use edge.target_pk for rows from get_edges_from and edge.source_pk for rows from get_edges_to, instead of deriving it from edge_def.direction. Add an execution test for multi-hop undirected patterns.

> **Verification:** VERIFIED by hand. For `BOTH` direction, `edge_rows` mixes results of `get_edges_from` (neighbor = `target_pk`) and `get_edges_to` (neighbor = `source_pk`), but the binding at `pattern_match.cpp:377` selects `target_pk` for everything except pure-IN. For rows that came from `get_edges_to`, `target_pk` IS the current node, so undirected multi-hop MATCH binds the target variable to the source node itself.


### C6 Variable-length MATCH with undirected (BOTH) edges drops all incoming-edge expansions and emits wrong rows on fixed segments
- **Location:** `src/executor/variable_length_match.cpp:587`  
- **Category:** fake-implementation | **Severity:** critical | **Found by:** `impl:exec-graph-ops`

Same bug class as pattern_match multi-hop, in two places. BFS expansion (lines 586-589): `Value nbr_pk = (edge_def.direction == TraverseDirection::IN) ? edge_row.source_pk : edge_row.target_pk;` — for BOTH, rows from get_edges_to have target_pk == entry.current_pk, which is always in entry.visited, so every incoming edge is silently skipped: undirected quantified patterns like (a:persons)-[r:knows]-{1,4}(b:persons) behave as OUT-only. Fixed-length segments (lines 464-468) have the identical wrong resolution with no visited set, so incoming edges emit rows binding tgt_var to the source node itself. tests/unit/test_variable_length_match.cpp line 162 (VarLenParse.UndirectedQuantifier) only asserts the PARSED direction is BOTH; no test executes a BOTH pattern.

**Why it matters:** Undirected variable-length MATCH silently returns incomplete results (only OUT-reachable nodes), and mixed fixed+variable patterns with an undirected fixed segment return wrong bindings. No error is surfaced. The only BOTH coverage is a parser test, giving false confidence the feature works.

**Suggested fix:** Resolve the neighbor per source index (target_pk for get_edges_from rows, source_pk for get_edges_to rows) in both the fixed-length and BFS branches, mirroring PatternMatchOperator::execute_single_hop. Add execution-level tests for undirected quantified patterns.

> **Verification:** VERIFIED by hand. Same root bug as pattern_match: at `variable_length_match.cpp:587` the neighbor for incoming edges under `BOTH` resolves to the current node, which is already in `visited` (`:590`), so every incoming-edge expansion is silently dropped from undirected variable-length traversals.


### C7 Wire-protocol SAVEPOINT / ROLLBACK TO SAVEPOINT are name-tracking no-ops that report success without rolling anything back
- **Location:** `src/server/session.cpp:585`  
- **Category:** fake-implementation | **Severity:** critical | **Found by:** `impl:server`

Session::try_handle_command intercepts "SAVEPOINT ", "RELEASE ", and "ROLLBACK TO " before the statement ever reaches the query executor (session.cpp:308-316). The handlers only manipulate a std::deque<std::string> of names: create_savepoint does `savepoints_.push_back(name)` (line 215) and rollback_to_savepoint just erases names after the match and flips txn_state_ (lines 241-265), then try_handle_rollback_to returns `qr.message = "ROLLBACK"` success. No call into the engine or TransactionManager is ever made, even though the parser supports SAVEPOINT/ROLLBACK TO (src/parser/parser.cpp:2721-2737) and TransactionManager implements real savepoint()/rollback_to_savepoint() with write-set restoration (src/txn/txn_manager.cpp:155-212).

**Why it matters:** A client that runs BEGIN; INSERT a; SAVEPOINT s; INSERT b; ROLLBACK TO s; COMMIT over the PostgreSQL wire protocol receives success for the ROLLBACK TO, but row b is silently committed anyway. That is silent wrong data on a mainline SQL path. (Distinct from the tracked GDB-616 rollback-compensation work: here the statement never even reaches the transaction layer because the protocol session swallows it.)

**Suggested fix:** Stop intercepting SAVEPOINT/RELEASE/ROLLBACK TO in Session::try_handle_command and forward them to the query executor so the parser/TransactionManager path handles them, or have the session handlers call into the engine. Until real rollback works end-to-end, return a NOT_IMPLEMENTED error (SQLSTATE 0A000) instead of fake success.

> **Verification:** VERIFIED by hand. `Session::rollback_to_savepoint` (`src/server/session.cpp:241`) only erases names from the `savepoints_` deque and flips `txn_state_` FAILED -> IN_TRANSACTION. No call into the transaction manager; no data is rolled back. A client that does `SAVEPOINT s; UPDATE ...; ROLLBACK TO s; COMMIT` silently commits the update. Worse, recovering FAILED -> IN_TRANSACTION allows committing a transaction that already had a failed statement.

## 2c. Phase-2 findings: the transaction layer does not exist (VERIFIED 2026-06-10)

Phase 2 audited `src/txn/` and the executor core by hand. The headline: **SixSevenDB has no working transactions, and the entire `src/txn/` module is dead code.**

### C9 BEGIN/COMMIT/ROLLBACK return errors to the client; no statement is ever transactional
- **Location:** `src/executor/planner.cpp:333`, `src/server/session.cpp:612`, `src/server/pg_protocol.cpp:1554`
- **Category:** fake-implementation | **Severity:** critical | **VERIFIED** (static chain, every link checked)

The parser produces `BeginStmt`/`CommitStmt`/`RollbackStmt` (`parser.cpp:2709-2719`); the binder passes them through (`binder.cpp:804`); `QueryEngine::execute` has no handler for them, so they fall to `execute_plan`; the planner's dispatch ends with `make_error(NOT_IMPLEMENTED, "planner does not support this statement type")` (`planner.cpp:333`). Over the wire, `pg_protocol.cpp:1562-1570` forwards that error to the client. So `BEGIN` errors out, `txn_state_` never becomes IN_TRANSACTION, and every statement auto-commits with no undo. `Session::update_transaction_state` (`session.cpp:612`) is a string-matching state machine layered on top of an engine that has no transaction support whatsoever.

**Corroboration:** no test in the 344-file suite ever runs `execute("BEGIN")`; `test_session.cpp` simulates success by calling `update_transaction_state("BEGIN", true)` directly. Combined with C5 (savepoints are name-tracking no-ops), the wire protocol presents transaction semantics that do not exist.

### C10 The entire `src/txn/` module (~1,100 lines) is production dead code; there is no MVCC
- **Location:** `src/txn/` (mvcc.cpp, txn_manager.cpp, lock_manager.cpp, deadlock_detector.cpp, vacuum.cpp)
- **Category:** unused-code / fake-implementation | **Severity:** critical | **VERIFIED** (repo-wide grep per symbol)

Zero production references outside `src/txn/` itself: `TransactionManager`, `LockManager`, `DeadlockDetector` (only caller: the dead `lock_manager.cpp:239`), `Vacuum`, `is_visible`, `Snapshot`, and `MvccTupleHeader` are all referenced only by their own module and by tests. There is no tuple versioning anywhere in the live path: `UpdateOperator` calls `heap_.update_tuple` which overwrites in place (`update.cpp:76`), `table_heap.cpp` contains no xmin/xmax/version fields, and scans perform no visibility checks. Consequences: no snapshot isolation, no write-write conflict detection (last-writer-wins between concurrent sessions), no row/table locking, and `is_dead`-based vacuum can never run. The MVCC visibility logic itself (`mvcc.cpp`) is correct PostgreSQL-style code — it is simply never called. CLAUDE.md's "Key Patterns: MVCC: Tuple versioning with xmin/xmax for transaction isolation" and the isolation-level plumbing (`default_transaction_isolation` session variable, `IsolationLevel` enum) describe a system that is not wired in.

### C11 VACUUM and ANALYZE parse and bind, then fail with "planner does not support this statement type"
- **Location:** `src/planner/binder.cpp:2881`, `src/executor/planner.cpp:333`
- **Category:** poor-ux / fake-implementation | **Severity:** high | **VERIFIED**

`VacuumStmt` is parsed, validated by the binder (including table-reference checks at `binder.cpp:2864-2881`), then falls through `execute_plan` to the planner's NOT_IMPLEMENTED default. The user gets a misleading error naming "the planner" for a maintenance command the grammar advertises. (`Vacuum`'s actual implementation in `src/txn/vacuum.cpp` is part of the dead module above.)

### Phase-2 secondary findings (verified, medium)

- **Integer division returns FLOAT64:** `eval_arithmetic` routes all `DIVIDE` through `to_double` (`expr_evaluator.cpp:256`), so `SELECT 7/2` yields `3.5`. PostgreSQL returns `3` for int/int division — a silent semantic divergence for ported SQL.
- **No integer-overflow checks in arithmetic:** the `both_integer` fast path (`expr_evaluator.cpp:256+`) adds/multiplies `int64_t` with no overflow detection; results wrap silently (PostgreSQL raises `numeric value out of range`).
- **DECIMAL arithmetic confirmed to go through `double`** (`expr_evaluator.cpp:282-283`), confirming the phase-0 lead: DECIMAL is precision-lossy in every arithmetic expression, on top of scale being discarded at the catalog (H1) and storage truncation (H6/C3).

### Phase-2 positive results (claims checked and cleared)

- `mvcc.cpp` visibility rules are correct (self-visibility, aborted/active xmin/xmax, snapshot window) — the code is sound, just unreachable.
- Window functions ARE wired into the live planner (`planner.cpp:1465-1478` constructs `WindowOperator`); the phase-0 survey lead claiming otherwise was wrong.
- NULL three-valued logic is present in arithmetic, comparison, and AND/OR short-circuit paths (`expr_evaluator.cpp:251`, `:317`, `:368-377`).
- The "two planners" are not duplicates: `src/planner/` is the semantic layer (binder/type_resolver — live), `src/executor/planner.cpp` is the physical planner (live). The decorative parts of `src/planner/` are exactly the optimizer/cost-model/statistics files (H17).

## 2d. Phase-3 findings: executor relational operators and infrastructure (VERIFIED 2026-06-10)

### C12 B+tree and hash secondary indexes are never maintained by DML — index scans return wrong results after any post-index write
- **Location:** `src/executor/insert.cpp:309` (BM25 only), `src/executor/update.cpp:81-98` (BM25 only), `src/executor/delete.cpp:43-56` (BM25 only), `include/sixseven/executor/index_manager.h` (no per-row API)
- **Category:** fake-implementation | **Severity:** critical | **VERIFIED** (static chain + API surface + test-ordering corroboration)

`IndexManager`'s entire public API is build/load/rebuild/flush/drop/reindex plus `append_hnsw_rid` — there is no per-row insert/delete-key operation at all. The DML operators maintain only BM25 postings (and HNSW receives inserts via the embedding-store callback, `query_engine.cpp:315-345`). Consequences after `CREATE INDEX`:

- **INSERT:** the new row is absent from every B+tree/hash index; an indexed equality/range query silently misses it.
- **DELETE:** the index keeps the dead RID; the index-only scan path (`index_scan.cpp:68`, which deliberately skips the heap fetch) returns values for deleted rows.
- **UPDATE of an indexed column:** the index still maps the old key; queries for the new value miss the row, and old-key lookups dredge it up (the residual predicate hides this on the heap-fetch path but not on the index-only path).
- **HNSW:** maintained on INSERT only; UPDATE/DELETE leave stale vectors in the graph.

**Why no test caught it:** every index test inserts rows BEFORE creating the index (`test_index_manager.cpp:118-121`, `:154-156`; `test_create_drop_index.cpp` never inserts), so the maintenance path is never exercised. The author of `FlushPersistsLatestState` (H-finding above) even wrote "depends on whether INSERT goes through the index manager" — the uncertainty was noticed and tested around instead of resolved.

**Suggested fix:** add `insert_entry(rid, values)` / `remove_entry(rid, values)` to IndexManager, call them from the three DML operators (and from UPDATE with old+new values), or mark indexes stale and force REINDEX before use. Add regression tests with insert-after-index ordering.

### Phase-3 secondary findings (verified, medium)

- **`hash_join.cpp:30-53` duplicates the flawed `ValueHash`:** a local copy of the hash visitor in `include/sixseven/common/value_hash.h`, including its hash-everything-else-to-0 branch. Joins keyed on DATE/TIMESTAMP/DECIMAL/UUID/INTERVAL/etc. put every row in one bucket: results stay correct (equality is rechecked via `compare`), but the join degrades to O(n·m). Duplicate code and brute force in one.
- **`COUNT(DISTINCT)` is O(n²) per group by explicit comment** (`hash_aggregate.cpp:266-273`: "Use a simple O(n^2) comparison for correctness"): values are accumulated in a vector and deduplicated pairwise at finalize.
- **BM25 maintenance failures are swallowed as warnings** (`update.cpp:92-97`, `delete.cpp:49-54`, `insert.cpp` same pattern): a failed postings update logs `SIXSEVEN_LOG_WARN` and continues, so the BM25 index silently drifts from the table with no error surfaced to the user.

### Phase-3 positive results (checked and cleared)

- Window functions are substantive: COUNT/SUM/AVG/MIN/MAX over real frames plus ranking functions, with empty/inverted frame detection (`window_function.cpp:168-380`).
- Sort-merge join handles duplicate key groups with a proper cross-product (`sort_merge_join.cpp:186-214`).
- Hash join NULL semantics are correct (NULL keys never match, `hash_join.cpp:57`; NULL probe keys skipped).
- Provider cache has an invalidation path; catalog persistence flushes through the buffer pool; demo data seeding is first-run-only by design (`main.cpp:271-274`).

### Wasserman-Faust closeness mixes weak-component size with directed reachability, producing scores > 1.0
- **Location:** `src/graph/closeness_centrality.cpp:221`  
- **Category:** fake-implementation | **Severity:** high | **Found by:** `impl:graph`

In the wasserman_faust branch: `wf_normalized = (nc - 1) / sum_dist` and `scaling = (nc - 1) / (total_nodes - 1)` where nc is the *weakly connected* component size (UnionFind over undirected edges, line 151) but sum_dist is the farness over only *directed-BFS-reachable* nodes (lines 184-201). The standard WF formula (e.g. NetworkX wf_improved) uses n = number of reachable nodes, not the undirected component size. Concrete counterexample: edges 1->2 and 3->2. For node 1: nc=3 (weak component {1,2,3}), reachable={1,2}, sum_dist=1, so wf_normalized = (3-1)/1 = 2.0 and closeness = 1.0*2.0 = 2.0 — closeness centrality on an unweighted graph is bounded by 1.0. **Why it matters:** The variant exists specifically for disconnected/asymmetric graphs, and on directed graphs where reachability is narrower than the weak component it returns inflated, mathematically impossible values (>1.0) with no error — plausible-but-wrong query results on the advertised mainline path.

**Suggested fix:** Use reachable_count (not weak-component size) in both factors: wf_normalized = (reachable_count - 1)/sum_dist; scaling = (reachable_count - 1)/(total_nodes - 1), matching the Wasserman-Faust definition. Add a directed-graph test where reachable_count < component_size.
